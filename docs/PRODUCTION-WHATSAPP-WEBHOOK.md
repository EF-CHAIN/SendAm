# Production WhatsApp webhook

The production callback is `https://<api-host>/webhook`. Meta verifies it with
a GET challenge and delivers events with POST. SendAm compares the GET verify
token in constant time and verifies every POST against the exact raw body using
the Meta app secret and `X-Hub-Signature-256`.

## Credentials and ownership

Configure these in the API deployment secret store:

```text
MESSAGE_TRANSPORT=meta
WHATSAPP_TOKEN=<long-lived system-user access token>
WHATSAPP_PHONE_NUMBER_ID=<Cloud API phone number ID>
WHATSAPP_VERIFY_TOKEN=<random deployment-owned secret>
WHATSAPP_APP_SECRET=<Meta app secret>
WHATSAPP_CALLBACK_URL=https://api.example.com/webhook
WHATSAPP_BUSINESS_ACCOUNT_ID=<WABA ID>
META_GRAPH_API_VERSION=vXX.X
```

Choose a currently supported Graph API version in the Meta developer console;
do not use an unversioned URL. Use a long-lived system-user token with only the
WhatsApp business-management and messaging permissions required by this
deployment. The verify token is generated by SendAm operators and entered on
both sides; it is not the access token or app secret.

Platform Engineering owns the deployed URL, TLS, secrets, workflow, and
availability. The WhatsApp Business administrator owns the Meta app, WABA,
system user, phone registration, app mode/review, and `messages` subscription.
Security owns app-secret and access-token rotation.

## Rollout

1. Deploy the API with all variables above. Production startup fails if any
   webhook credential or identifier is missing, or if the callback is not
   HTTPS.
2. Confirm `GET /health` succeeds and the callback URL is publicly reachable
   without authentication, redirects, query parameters, or a CDN-cached
   response.
3. Add `WHATSAPP_CALLBACK_URL`, `WHATSAPP_BUSINESS_ACCOUNT_ID`, and
   `META_GRAPH_API_VERSION` as variables in the protected GitHub `production`
   environment. Add `WHATSAPP_VERIFY_TOKEN`, `WHATSAPP_APP_SECRET`, and
   `WHATSAPP_TOKEN` as environment secrets.
4. Run **Configure production WhatsApp webhook** and enter
   `CONFIGURE_WHATSAPP_PRODUCTION`. The serialized workflow:
   verifies the deployed GET challenge, sets the WABA callback through Meta's
   `/{WABA-ID}/subscribed_apps` endpoint, reads the subscription back, accepts a
   correctly signed safe POST, and proves an invalid signature receives 403.
5. In the Meta app dashboard, ensure the app is live as appropriate and the
   WABA is subscribed to the `messages` field. Send a real message from an
   allowed test phone and confirm the expected reply.

The same validation can be run from a trusted operator host with
`npm run whatsapp:webhook:configure --workspace=apps/api`. It mutates the Meta
subscription and must not be run from an untrusted workstation.

## Compatibility and security boundary

The callback path and environment variable names already used by deployments
remain unchanged. Malformed verification GETs now return 400 instead of
falling through to a 200 response; wrong credentials continue to return 403.
This is an intentional fail-closed correction.

TLS protects the verify token and payload in transit. The app secret authenticates
POST bodies; the verify token only proves control during callback registration.
Never log request bodies, query strings, signatures, tokens, or app secrets.
Synthetic workflow POSTs contain no messages and cannot cause user or payment
side effects.

## Monitoring

Ship the structured API and workflow events to the production alert platform:

- `whatsapp_webhook_verification_succeeded`
- `whatsapp_webhook_verification_rejected`
- `whatsapp_webhook_signature_verified`
- `whatsapp_webhook_signature_rejected`
- `whatsapp_webhook_configuration_verified`
- `whatsapp_webhook_configuration_failed`

Alert on any configuration failure, sustained signature rejection, webhook 5xx
responses, Meta delivery failures, or absence of verified message events during
expected traffic. Track callback latency and queue age separately; a valid
signature does not prove downstream processing succeeded.

## Recovery and rotation

For failed GET verification, compare the exact HTTPS URL and verify token, check
for proxy redirects or query rewriting, and inspect rejection reason logs. For
POST 403s, ensure `WHATSAPP_APP_SECRET` belongs to the app sending the webhook
and that the proxy preserves the raw body. Do not “temporarily” disable
signature verification.

Rotate the system-user token by updating the API and GitHub secrets, testing an
outbound message, then revoking the old token.

### Safe Webhook App Secret Rotation

SendAm supports safe, zero-downtime rotation of the Meta `WHATSAPP_APP_SECRET` by allowing multiple comma-separated keys to be active simultaneously (e.g., `WHATSAPP_APP_SECRET=new_active_secret,previous_verification_secret`).

#### Step-by-Step Rotation Playbook:

1. **Rollout (Add New Secret):**
   - Retrieve the new App Secret from the Meta Developer Console.
   - Update the deployment environment variables: append the new secret as the first/primary key in `WHATSAPP_APP_SECRET` followed by a comma and the existing/old secret. (Format: `WHATSAPP_APP_SECRET=<new_secret>,<old_secret>`).
   - Re-deploy the API. Incoming webhooks signed with either the old secret or the new secret will verify successfully.
   - Check the API logs to verify webhooks are being successfully authenticated with the new secret (marked with `{ "verifiedBy": "active" }`) and the old secret (marked with `{ "verifiedBy": "previous_index_1" }`).

2. **Rollback (If Rotation Fails):**
   - If incoming signatures using the new secret fail or Meta does not recognize the new secret, rollback immediately by removing the new secret and restoring the previous secret as the primary secret in `WHATSAPP_APP_SECRET`.
   - Re-deploy the API on the original configuration.

3. **Retirement (Remove Old Secret):**
   - After a bounded rotation window (e.g., 24 hours of successful verification under the new secret and ensuring zero traffic verifying against `previous_index_1`), finalize the rotation.
   - Remove the old secret from the comma-separated list, leaving only the single new secret in `WHATSAPP_APP_SECRET`.
   - Re-deploy the API to complete retirement.

Rotate the verify token by updating the deployment and workflow secret
together, then rerun the workflow.

## Rollback

Keep the previous API deployment and secrets available. If the new callback
fails, restore the previous API version and callback URL, run the configuration
workflow with that URL, confirm subscription readback, and send a real message.
Do not delete the WABA subscription or revoke working credentials until the
rollback is verified. Reconcile any messages shown as failed in Meta delivery
logs after service is restored.
