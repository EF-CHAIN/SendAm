# SendAm issue draft set 291-340

This file contains a draft backlog of issue definitions numbered 291 through 340 for the SendAm project. Each item is written to be copied into GitHub as a tracked issue and includes a clear problem statement, required implementation scope, affected areas, and acceptance criteria.

---

## Issue 291: Harden wallet recovery and escrow key rotation for customer funds

Title: Add secure wallet recovery and escrow-key rotation workflow

Problem:
Customer wallet keys and recovery paths are critical to financial safety. If recovery or rotation is incomplete, a compromised or rotated key could leave funds inaccessible or vulnerable. The project needs a secure, auditable recovery and rotation model.

Required work:
- Define wallet recovery identity, ownership verification, and cooling-off policy.
- Add escrow or backup key rotation logic with explicit version tracking.
- Add safe rollback and failure recovery steps.
- Ensure all recovery operations are audit logged.

Acceptance criteria:
- Recovery flow cannot be triggered without verified ownership or compliance checks.
- Rotation is versioned, resumable, and observable.
- Failed recovery and rotation events are logged and visible to operators.

Labels: security, wallet, compliance, operations, priority: critical

Title: Create periodic wallet state snapshots for recovery and incident review

Problem:
When incidents occur, support and operators need historical wallet state snapshots to reconstruct what happened and determine the right response.

Required work:
- Define snapshot frequency and retention for wallet state.
- Store key wallet and payment state for review.
- Ensure snapshot data is queryable and protected.

Acceptance criteria:
- Wallet snapshots are generated on defined intervals or major events.
- Snapshots are recoverable for support and incident review.
- Snapshot storage is auditable and retention-managed.

Labels: wallet, operations, audit, reliability

## Issue 339: Add infrastructure cost and usage tracking for services and providers

Title: Track infrastructure usage and cost by service, provider, and resource tier

Problem:
As the platform grows, infrastructure costs and usage patterns need to be visible to engineering and leadership. Without this, spend can grow without insight.

Required work:
- Track usage for database, Redis, blockchain, messaging, and hosting resources.
- Add cost attribution and thresholds.
- Surface this data through operations dashboards or reports.

Acceptance criteria:
- Usage and cost can be attributed to the relevant service or provider.
- Alerting triggers when spend or usage exceeds thresholds.
- Cost reporting is integrated into operational review.

Labels: operations, monitoring, backend, cost-management

## Issue 340: Add a launch-readiness checklist and sign-off workflow before production release

Title: Require a signed launch-readiness checklist before real-money rollout

Problem:
The project has many technical pieces in place, but a single launch gate is required before any real-money usage. Without a formal sign-off process, risk remains high.

Required work:
- Define launch-readiness sign-off checklist with product, engineering, security, compliance, and operations owners.
- Require evidence for deployment, monitoring, security, and incident preparedness.
- Block production release if any mandatory gate is incomplete.

Acceptance criteria:
- Real-money release requires explicit sign-off by required roles.
- Launch readiness is documented and auditable.
- Production deployment cannot proceed without evidence and approvals.

Labels: launch-readiness, compliance, security, operations, deployment
